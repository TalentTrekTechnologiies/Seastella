The SoW asserts its own authority: it “consolidates and reconciles three inputs” (§1) and “forms the baseline for pilot development” (§19). It makes ten material overrides over the earlier specifications. Two of them change the shape of the system.

01

The Spare is the asset — not the Equipment

The single most consequential correction in the analysis. The earlier specifications modelled Equipment as the serviceable record carrying serial number, running hours and service history. The SoW overrides this.

“‘Equipment’ is a category (e.g., Radar, ECDIS, GPS); the individual serviceable item within that category — whether a full unit or a component of one — is a ‘Spare,’ and it is the Spare, not the category, that carries a service history.” — SoW §9

Spares nest recursively, mirroring the VMP template’s decimal IDs. Service requests, troubleshooting, running hours, maintenance and documents all attach to the Spare.

Why this had to be settled first

Building Equipment as the asset would have put running hours, service history and maintenance scheduling on the wrong entity — breaking the VMP import, every dashboard and the service-history requirement simultaneously, and discovering it only at integration.

02

The operational flow, and the gate inside it

One unified Service Request replaces the earlier two-spreadsheet handoff. The workflow runs in three phases, and one transition inside it is a hard server-side guard rather than a convention.

A

Service Request & assisted troubleshooting

CaptainRaises request on Spare → SystemTroubleshooting assistant → Captain ↔ CoordinatorLive agent chat → Ship ManagerOperational approval
B

Invoice acceptance gate

CoordinatorReviews full log → CoordinatorRaises invoice → Ship ManagerAccepts / rejects
Hard guard. A Service Engineer cannot be assigned until the invoice is accepted. Enforced in the state machine — assignEngineer() is rejected unless status is INVOICE_ACCEPTED. This is an acceptance criterion (SoW §18), not a UI rule, and it is tested on the failure path.
C

Execution & completion

EngineerPerforms service → Engineer → CoordinatorCompletion report → Coordinator → Ship ManagerRelayed update → SystemHistory + next due recalculated
Reporting chain. The Engineer reports to the Coordinator only — never directly to the Ship Manager or Technical Head. The Coordinator’s relay is the Ship Manager’s single channel for completion. The Engineer has no transition that reaches either role.
03

Maintenance colour status

One engine calculates due status; dashboards, spare screens, alerts and reports all consume it. Thresholds are configuration rows, never constants — and status is never recomputed in a frontend component.

Each status also carries a distinct shape — dot, half-dot, triangle, square — so it survives greyscale printing and colour-vision deficiency, which matters when reports reach class surveyors.

Ambiguity found in the published bands

“10–15 days” and “1–9 days” do not meet — 9 < d < 10 is unclassified. Harmless under whole-day arithmetic, but any fractional-day or timezone-boundary calculation lands in the gap. Implemented as half-open bands so no day is unclassified, and raised with Seastella as open item OI-02.

04

Architecture

A modular monolith — one deployable Spring Boot application built from Maven modules with boundaries the build enforces, and contracts written so any module can be extracted later without a rewrite.

The SoW is specific about this shape: “clear module boundaries … without over-fragmenting into microservices for the pilot, to keep MVP delivery risk low” (§13). True microservices were rejected — a distributed transaction across the invoice-acceptance gate would be the riskiest thing in the build, for no pilot benefit.

platform-core

Audit, documents, configuration, domain events, error envelope

identity-access

Users, six roles, org/vessel assignment, JWT, scope resolution

fleet

Organization, vessel, equipment category, the Spare tree, parts stock

maintenance

Due-date engine, colour status, thresholds, alert generation

service-request

The request aggregate and its state machine

troubleshooting

Rule engine, session log, live agent chat

invoice

Invoice record and the acceptance gate

masterdata-import

VMP template, validate → preview → confirm → commit

activity-feed

Platform-wide real-time feed over SSE

notification

In-app and email fan-out, configurable recipients

reporting

Role-scoped reports and PDF export

app

Boot entry, security filter chain, composition root

Four rules keep extraction cheap

  • Every module exposes only api; internal is unreachable across boundaries.
  • No shared entities and no cross-module SQL joins — modules exchange DTOs and IDs.
  • Side effects travel as domain events, not calls, behind a publisher interface.
  • Each module owns its schema namespace and its own migrations.

ArchUnit tests fail the build on any violation. Boundaries that are only documented are not boundaries.

Vessel isolation is structural

Every access rule reduces to one question — which vessels may this principal touch — so it is answered once, in a request-scoped resolver, and applied three ways: method security for the coarse role check, a Hibernate filter that narrows every scoped query in SQL, and an aggregate guard on each write path. A forgotten WHERE clause still cannot leak another vessel’s rows. Out-of-scope resources return 404, never 403, so IDs cannot be probed for existence.

05

Six role dashboards

Genuinely different compositions, not one layout with cards hidden by role. Every figure is served by a role-scoped endpoint — none is hard-coded.

Platform Admin

Entire platform
  • Live platform-wide activity feed
  • Organizations, users, vessels
  • Threshold & content configuration
  • Full audit trail

Technical Head

All vessels in own org
  • Fleet spare health, due & overdue
  • Open requests by workflow stage
  • Resolved without cost vs engineer visit
  • Invoices fleet-wide, count & value

Ship Manager

Allocated vessels only
  • Requests awaiting operational review
  • Invoices awaiting acceptance
  • Assigned vessel status
  • Completion via Coordinator relay

Captain

One assigned vessel
  • Raise a Service Request — primary action
  • My requests & approval history
  • Active conversations
  • Running hours, spares due
No invoice values — SoW §12

Service Coordinator

Assigned service scope
  • Pipeline board by stage
  • Live chat queue awaiting reply
  • Accepted invoices ready to assign
  • Reports pending relay to Ship Manager

Service Engineer

Assigned jobs only
  • Today’s schedule & upcoming jobs
  • Job detail with full context
  • Work log, parts, attachments
  • Completion report to Coordinator
No invoice amounts, no other vessels

The decision to make before scope freeze

V-01 and V-02 are the two that remove committed brief scope. Either accept the SoW’s Phase-2 classification, or raise a Change Request under §19 and extend the five-week plan by an estimated 1.5–2 weeks. The data model already carries the shortage trigger a requisition would start from, so either path is open — but the timeline differs.

09

Next

Phase A is complete and committed. Implementation follows the SoW’s five-week plan:

  • Week 1 — authentication, RBAC, the delegated provisioning chain (Platform Admin → Technical Head → Ship Manager → Captain)
  • Week 2 — Spare tree per the VMP structure, the Excel import engine, vessel and spare screens
  • Week 3 — Service Request, troubleshooting assistant, live agent chat
  • Week 4 — invoice acceptance gate, service execution, maintenance engine and alerts
  • Week 5 — the six dashboards, activity feed, reports, security testing, deployment

The design system and application shell are built first, before any dashboard — six dashboards is precisely the situation where skipping that produces six divergent implementations.
