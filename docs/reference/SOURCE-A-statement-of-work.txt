1. Document Purpose
This Statement of Work (SoW) defines the functional scope, operational flows, role-based dashboards, data structures and implementation plan for the Maritime Navigation Equipment Asset & Service Management Platform being proposed by Talent Trek Technologies for Seastella Maritime.
This document consolidates and reconciles three inputs reviewed for this engagement:

2. Background & Context
Seastella Maritime, a venture of Pucho Consultant Private Limited, provides technical and navigational-equipment management support to ship-management companies operating merchant vessel fleets. Vessel operators today track bridge and navigational equipment — ECDIS, radar, gyrocompass, GMDSS equipment, AIS, GPS and related systems — largely through manual records and spreadsheets, with limited visibility for shore-side management into fleet-wide equipment health, service due-dates and critical spare availability.
Talent Trek Technologies is engaged to design and build a centralized digital platform that gives every role — from the Captain onboard to the Technical Head overseeing the fleet — a single, role-appropriate view of equipment status. Vessel and equipment master data continues to be onboarded through the familiar VMP Excel structure, while day-to-day issue and service reporting moves to a single in-app Service Request, backed by immediate, guided troubleshooting support — removing the earlier two-document (issue Excel + service-request Excel) handoff.
3. Project Objective
The platform will act as the single source of truth for navigational and bridge equipment across Seastella’s managed fleet, enabling:
Centralized vessel and equipment master data, structured around the existing VMP data format.
A self-service administrative hierarchy: the Platform Admin provisions each Organization and its Technical Head; the Technical Head creates Ship Managers and allocates vessels to each; each Ship Manager then assigns the Captain to their own vessels — so fleet structure stays in Seastella’s hands day-to-day (Section 4.1).
A single Service Request raised directly by the Captain — no separate issue file and service-request file to reconcile.
An Automated Troubleshooting Assistant that engages the moment a request is raised, helping the crew identify the likely root cause and, where possible, apply a temporary fix while a permanent service is arranged.
Role-based approval and routing: Ship Manager operational approval of each request, escalation to a Live Agent Chat if automated troubleshooting doesn’t resolve it, and a Ship Manager acceptance of the Service Coordinator’s invoice before a Service Engineer is ever assigned. Payment settlement itself is out of scope for now.
Real-time, role-appropriate dashboards — particularly a fleet health dashboard for the Technical Head.
A single, continuous service and invoice history per Spare — covering automated troubleshooting outcomes, live-agent sessions, invoices and Service Engineer visits alike — maintained centrally by Seastella and fully visible to the Platform Admin.
A foundation that can be extended in later phases to AI-driven chat, payment settlement/gateway processing, and spare requisition/RFQ automation, as detailed in the reference specification.

6. Core Operational Flow (Pilot Scope)
A single, unified workflow forms the operational core of this engagement, replacing the earlier two-document (issue Excel + service-request Excel) design. The Captain raises one Service Request directly against the Spare record — the individual serviceable item within an Equipment category (Section 9). The flow runs in three phases: (A) troubleshooting, with escalation to a live human agent if automated checks don’t resolve it; (B) an invoice acceptance gate — the Service Coordinator cannot assign a Service Engineer until the Ship Manager has accepted an invoice for the job (payment settlement itself is confirmed out of scope for now — Section 15); and (C) service execution and completion. Every step is logged permanently against the Spare by Seastella, and every update across the platform is visible to the Platform Admin in real time.

Step-by-step:
The Captain identifies an issue with a Spare and raises a single Service Request directly from its record — Spare, problem description, priority, and supporting photos/video. No Excel file is involved at this step.
On submission, the system immediately opens the Automated Troubleshooting Assistant — a Spare- and problem-specific guided chat (e.g., for an ECDIS display-fan / GPS input failure: verify GPS receiver status → check signal → check NMEA/interface connection → record error code).
If the guided checks don’t resolve it, the Captain can escalate the same request to a Live Agent Chat — a real-time conversation with the Seastella Service Coordinator for further diagnosis or a temporary workaround, so the vessel isn’t left waiting on the Spare while a permanent service is arranged.
Every question, check and message across both the automated session and the live chat is logged against the request, whether or not it fully resolves the issue.
The Ship Manager is notified as soon as the request is raised and reviews/approves it on the same record — an operational approval, not yet a financial one.
On approval, the request (with its full troubleshooting and live-chat log attached) is forwarded to the Seastella Service Coordinator. The Platform Admin’s activity feed reflects the request from the moment it is raised.

Step-by-step:
The Service Coordinator reviews the full troubleshooting and live-chat log. If the issue is already resolved, the Coordinator closes the request with the fix recorded as the resolution — no invoice is raised and no cost is incurred.
If the issue remains unresolved and a Service Engineer visit is needed, the Coordinator raises an invoice against the request — a cost description for the service — and sends it to the Ship Manager.
The Ship Manager reviews and accepts, rejects or queries the invoice. This is a distinct acceptance step — separate from the earlier operational approval in Phase A.
The Service Coordinator cannot assign a Service Engineer until the invoice is accepted. No engineer is dispatched against an unaccepted invoice.
Once accepted, the Coordinator assigns the appropriate Service Engineer, who receives the full context: original report, troubleshooting/live-chat log, and the accepted invoice.
Per Seastella’s confirmation, this is an invoice ACCEPTANCE workflow only — the Coordinator raises the invoice and the Ship Manager accepts or rejects it in-app. Actual payment settlement (collecting or transferring money) is explicitly out of scope for this engagement and remains part of Seastella’s existing finance process (Section 15).

Step-by-step:
The Service Engineer performs the service and reports work performed, parts used (where applicable) and final outcome back to the Service Coordinator only — the Engineer does not update the Ship Manager or Technical Head directly.
The Service Coordinator reconciles the final cost against the accepted invoice (flagging any variance) and updates the Ship Manager. This is the single channel through which the Ship Manager learns a service is complete.
The Spare’s service history and its invoice record are updated together, and the next-service-due date is recalculated where applicable.
Every request — whether closed without cost in Phase B or completed by a Service Engineer visit — remains permanently attached to that Spare’s service history, maintained centrally by Seastella.
The Technical Head and Platform Admin see the full status — Reported → Troubleshooting → (Live Agent, if escalated) → Operationally Approved → Invoice Raised → Invoice Accepted → Assigned → Completed — on their dashboards throughout, without waiting on manual relay; the Platform Admin’s view spans every organization and vessel on the platform.

9. Equipment & Spare Master and Vessel Data Structure
The VMP Vessel Creation Template supplied by Seastella is adopted as the platform’s master-data structure, so no re-mapping is required for existing vessel data. “Equipment” (e.g., Radar, ECDIS, GPS, EPIRB) is a category used for grouping and fleet-level reporting. The individual serviceable item within that category — a full unit (e.g., GPS 1) or a component of a larger unit (e.g., the Display Fan on an X-Band Radar) — is a “Spare.” Service Requests, troubleshooting, running hours, maintenance and documents are all raised and tracked at the Spare level, mirroring the VMP template’s own decimal ID structure (e.g., 13 Radar → 13.1 X-Band Radar → 13.1.2 Display Fan). A Spare can itself be the parent of further Spares, exactly as in the template.
9.1  Vessel-Level Fields
Vessel Name, IMO Number, MMSI, Call Sign, Flag, Class, Area, Vessel Type, DWT
9.2  Equipment Category
Category Name (e.g., Radar, ECDIS, GPS, EPIRB, GMDSS, VDR/SVDR, Gyro) — used to group Spares for dashboards and reports; not itself a serviceable record.
9.3  Spare-Level Fields
Spare ID/Description, Equipment Category, Parent Spare (where nested, e.g., Display Fan under X-Band Radar)
Make, Model, Serial Number
Date of Installation, Software Version
Expiration Date, Last Annual Service / Survey / APT Date
Running Hours, where applicable (e.g., magnetron running hours)

18. Acceptance Criteria
The pilot MVP will be considered functionally ready when:
Users can log in securely and access only their assigned organization/vessel(s).
A Platform Admin can create an Organization and its Technical Head user; a Technical Head can create Ship Manager users and allocate vessels to each; a Ship Manager can assign a Captain to each of their vessels (Section 4.1).
A Captain can raise a single Service Request directly from a Spare record, with description, priority and attachments.
The Automated Troubleshooting Assistant engages immediately on a new request, presents Spare/problem-specific guided checks, and logs the outcome (resolved / temporary fix / unresolved).
If unresolved, a Captain can escalate a request to a Live Agent Chat with the Service Coordinator, and the full transcript is logged against the request.
A Ship Manager can review, approve, reject or request clarification on the same request record (operational approval) — no separate file.
An approved request updates the relevant Spare record and is reflected on the Technical Head’s Fleet Dashboard.
A Service Coordinator can close a request resolved without cost, or raise an invoice against an unresolved request.
A Ship Manager can accept or reject an invoice; a Service Engineer can be assigned by the Service Coordinator only after invoice acceptance — the system blocks assignment on an unaccepted or rejected invoice. No payment is collected or transferred by the platform.
A Service Engineer’s completion report reaches the Service Coordinator only; the Ship Manager is updated by the Coordinator, not directly by the Engineer.
Completed services update the Spare’s service history and invoice record, and recalculate the next-service-due date.
Maintenance colour-status changes automatically as due dates approach or pass.
All five role dashboards (Section 8) display correct, role-scoped data — including invoice visibility limited to Ship Manager, Service Coordinator, Technical Head and Platform Admin — and the Platform Admin’s activity feed reflects every request, troubleshooting outcome, live-chat escalation, invoice, approval, escalation and completion across the platform in real time.
Every approval, rejection, upload, invoice action and service update is present in the audit trail.
