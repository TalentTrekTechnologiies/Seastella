Software Requirements Document
Maritime Navigation Equipment Asset & Service Management Platform

1. Purpose of the Application
The application will provide a centralized web-based platform for managing:
Companies
Ships / Vessels
Vessel users
Equipment
Equipment service history
Maintenance
Surveys
Health checks
Running hours
Critical spares
Service requests
Service providers
Payments / service costs
Documents
Alerts and notifications
Fleet-level dashboards and reports
The system must provide clear ownership and control at every level.
The primary hierarchy will be:
Platform → Company → Vessel → Equipment → Service / Maintenance / Documents / Spares


2. Core Business Hierarchy
2.1 Platform Administrator
The highest-level system administrator will have control over the entire application.
Responsibilities
Create and manage companies
Create and manage users
Assign company administrators
View all vessels
Manage system-wide configurations
Configure maintenance rules
Manage master data
Monitor system activity
Manage permissions
View system-level reports
Manage notification settings
The platform administrator should have visibility across all organizations while maintaining strict audit logging.

3. Company Management
Each customer/company will have its own isolated environment.
Company Administrator
A company administrator can:
Create vessels

View company vessels
Manage vessel information
View equipment
Assign users to vessels
Manage service activities
Review service requests
Monitor maintenance
Review service costs/payments
View company reports
A company user must not be able to access another company's information.

5. User & Role Management
The system must implement role-based access control.
Proposed Roles
5.1 Super Administrator
Full system access.
5.2 Company Administrator
Controls the company's vessels, users and operational data.
5.3 Marine Administrator / Service Coordinator
Manages service operations, maintenance schedules, service requests and coordination.
5.4 Vessel Manager / Superintendent
Can monitor assigned vessels and approve/coordinate vessel-level activities.
5.5 Master
Can access operational information for the assigned vessel and raise service/maintenance requests.
5.6 Chief Engineer
Can manage equipment-related operational information, running hours, service records and maintenance information for the assigned vessel.
5.7 Service Provider / Technician
If enabled, can access only assigned service jobs and relevant equipment information.

6. Permission Model
Access should be controlled at multiple levels.
Level 1 – Organization
User belongs to a specific company.
Level 2 – Vessel
User is assigned to one or more vessels.
Level 3 – Equipment
User access is inherited from the vessel unless specifically restricted.
Level 4 – Function
Different users can have different permissions:
View
Create
Edit
Approve
Delete
Export
Manage payments
Manage users
Manage configuration
Example:
A Chief Engineer assigned to Vessel A should not be able to view Vessel B.
A Company Administrator can view all vessels belonging to their company.
A Super Administrator can manage the entire platform.

13. Payment Control
Payment permissions must be separated from normal operational permissions.
For example:
Chief Engineer
→ Can raise service request
Service Coordinator
→ Can coordinate service
Company Administrator / Authorized Finance User
→ Can approve service cost/payment
Super Administrator
→ Can manage system-level financial configuration
This separation prevents unauthorized users from changing financial information.


14. Maintenance Scheduling
The system will automatically calculate maintenance due dates based on configurable rules.
Maintenance can be based on:
Calendar interval
Running hours
Service interval
Manufacturer recommendation
Custom company rule
Example:
Equipment requires service every 180 days.
If the last service was on 1 January:
Next Service → 30 June
The system should automatically monitor the approaching deadline.

15. Deadline & Colour-Coded Status System
This is a key dashboard requirement.
The application should visually communicate how close an activity is to its deadline.
Proposed Colour Logic
Green – Normal
More than 15 days remaining.
Yellow – Approaching
10–15 days remaining.
Orange – Urgent
1–9 days remaining.
Red – Overdue
Deadline has passed.
Example
Maintenance due on 30 September:
Remaining Time | Status
16+ days | 🟢 Green
10–15 days | 🟡 Yellow
1–9 days | 🟠 Orange
0 / Due Today | 🔴 Red
Overdue | 🔴 Red / Overdue
The exact thresholds can be configured by the administrator rather than hard-coded.

16. Dynamic Status Colour
The colour must automatically change as the deadline approaches.
Example:
Day 20
🟢 Normal
Day 15
🟡 Approaching
Day 9
🟠 Urgent
Day 1
🟠 Urgent
Due Date
🔴 Due Today
Day +1
🔴 Overdue
No manual status update should be required.

28. Security Requirements
Security is a major requirement of the application.
Authentication
Secure login
Strong password policy
Secure session management
Password reset
Account lock/rate limiting where appropriate
Authorization
Every API request must verify that the logged-in user has permission to access the requested company/vessel/equipment.
Frontend hiding alone is not sufficient.
The backend must enforce permissions.

29. Multi-Tenant Data Isolation
The application must prevent cross-company data access.
Example:
Company A
User A → Vessel A1, Vessel A2
Company B
User B → Vessel B1, Vessel B2
User A must never be able to access:
Company B → Vessel B1
even if they attempt to manipulate URLs, IDs or API requests.
This is one of the most important security requirements.

The MVP should be considered functionally ready when:
A company can be created.
Vessels can be created under a company.
Users can be assigned to appropriate vessels.
Equipment can be registered under vessels.
Equipment service history can be recorded.
Running hours can be updated.
Critical spares can be tracked.
Maintenance schedules can be configured.
Due dates are calculated automatically.
Status colours change automatically according to configured thresholds.
Overdue items become red.
Service requests can be raised and tracked.
Service costs/payment information can be managed by authorized users.
Excel/CSV data can be validated before import.
Alerts are generated automatically.
Users cannot access unauthorized vessels or companies.
Important actions are recorded in an audit trail.
Documents can be securely uploaded and accessed.
Dashboard displays operational status.
Application can be deployed to production.

40. Key Requirement
The application should be designed as a secure, scalable and maintainable product, not merely a collection of screens.
The technical implementation should cover:
Architecture → Database → Backend → Frontend → APIs → Business Logic → Automation → Security → Deployment
The original scope likewise defines the role as end-to-end technical ownership rather than simply screen development.

Final Requirement Summary
The core system should answer five questions immediately:
1. WHAT?
What equipment, service, maintenance or issue exists?
2. WHERE?
Which company and vessel does it belong to?
3. WHO?
Who owns, manages, reports, approves or services it?
4. WHEN?
When is the next service, survey, health check, payment or deadline?
5. WHAT IS THE STATUS?
Is it:
🟢 Normal
🟡 Approaching
🟠 Urgent
🔴 Overdue / Critical
This should be reflected consistently throughout the dashboard and individual records.
